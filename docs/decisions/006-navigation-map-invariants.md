# 006. NavigationMap 생성 시 graph 불변조건을 검증

- 상태: 채택
- 결정일: 2026-08-19

## 맥락

잘못된 graph를 허용하면 PathPlanner가 실행될 때마다 입력 오류를 방어해야 한다. 생성된 `NavigationMap`은 별도 방어 없이 탐색할 수 있는 유효한 상태여야 한다.

## 결정

`NavigationMap`은 생성 시 Node와 Edge 전체를 검사하고 불변조건을 위반한 입력을 거부한다.

| 불변조건 | 처리 |
| --- | --- |
| 중복 `NodeId` | 거부 |
| 중복 `EdgeId` | 거부 |
| 존재하지 않는 Node를 참조하는 Edge | 거부 |
| 유효하지 않은 Edge 거리 | 거부 |
| `from`과 `to`가 같은 self-loop | 거부 |
| 서로 다른 `EdgeId`를 가진 parallel edge | 허용 |
| 여러 영역으로 단절된 graph | 허용 |
| Incoming과 outgoing Edge가 모두 없는 isolated Node | 거부 |
| Node 또는 Edge가 없는 빈 Map | 거부 |
| 두 개 이상의 Node로 이루어진 cycle | 허용 |

Self-loop는 대기나 회전 같은 제자리 행동으로 해석하지 않는다. 이러한 행동이 필요해지면 이동 Edge가 아닌 별도 runtime 행동으로 모델링한다.

Parallel edge는 출발지, 목적지, 거리가 같아도 별개의 물리적 통로일 수 있다. 각 Edge는 `EdgeId`로 구분하며 독립적으로 차단하거나 점유할 수 있다.

Graph 전체의 연결 여부는 불변조건으로 강제하지 않는다. 특정 출발지에서 목적지까지 도달할 수 없는 상태는 잘못된 Map이 아니라 PathPlanner가 표현할 정상적인 탐색 결과다.

모든 Node는 최소 하나의 incoming 또는 outgoing Edge에 연결되어야 한다. 편집 중 Node나 이동과 무관한 landmark는 완성된 routing graph에 포함하지 않는다.

완성된 `NavigationMap`은 최소 2개의 Node와 1개의 directed Edge를 가져야 한다. 내용을 작성 중인 빈 상태는 향후 별도 draft나 입력 모델이 담당한다.

양방향 통로와 순환형 동선을 표현할 수 있도록 cycle을 허용한다. 모든 Edge 거리가 양수이므로 Dijkstra는 비용이 증가하는 순환 경로를 최단 경로로 선택하지 않는다.

## 선택의 장점

| 관점 | 장점 |
| --- | --- |
| 오류 발견 | 잘못된 graph를 Map 생성 시점에 발견한다. |
| Edge 의미 | Edge를 서로 다른 Node 사이의 이동 관계로 유지한다. |
| 통로 표현 | 같은 두 Node를 연결하는 여러 통로를 자연스럽게 표현한다. |
| 실험 범위 | 독립된 작업 구역과 도달 불가능한 경로를 표현할 수 있다. |
| Node 의미 | 모든 Node가 실제 이동 graph에 참여한다. |
| Map 의미 | 모든 Map이 최소 하나의 실제 이동 관계를 가진다. |
| 실제 동선 | 양방향 통로, 순환 동선과 우회로를 표현할 수 있다. |
| PathPlanner | 입력 검증보다 경로 탐색에 집중할 수 있다. |
| 테스트 | 모든 `NavigationMap`이 동일한 기본 조건을 만족한다. |

## 감수하는 단점

| 단점 | 대응 |
| --- | --- |
| Map 생성 시 전체 검증 비용이 든다. | immutable Map의 안정성을 위한 일회성 비용으로 수용한다. |
| 제자리 행동을 Edge로 표현할 수 없다. | 대기와 회전은 필요할 때 runtime 행동으로 분리한다. |
| 실수로 중복 입력한 Edge도 별도 ID라면 허용된다. | 편집 기능에서 경고할 수 있지만 domain은 물리적으로 다른 통로일 가능성을 막지 않는다. |
| 통로 누락으로 단절된 Map도 생성될 수 있다. | 편집 기능은 경고하고 Scenario는 필요한 Mission의 도달 가능성을 검증한다. |
| Node 하나만 있는 Map이나 편집 중 Node를 표현할 수 없다. | 편집 상태와 landmark는 필요할 때 별도 모델로 분리한다. |
| 빈 Map을 편집 시작점으로 사용할 수 없다. | 작성 중 상태는 향후 별도 draft나 입력 모델로 표현한다. |

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| PathPlanner가 매번 검증 | Map 생성이 단순하다. | 알고리즘마다 검증이 중복되고 오류 발견이 늦어진다. |
| Self-loop 허용 | 제자리 행동을 graph에 넣을 수 있다. | 이동과 행동의 의미가 섞이고 양수 비용의 최단 경로에서는 쓸모가 없다. |
| Parallel edge 거부 | Graph와 중복 검사가 단순하다. | 여러 통로나 차선을 표현할 수 없고 일부 통로만 차단하기 어렵다. |
| 전체 연결 강제 | 통로 누락을 Map 생성 시 발견하기 쉽다. | 독립된 구역과 도달 불가능한 경로를 표현할 수 없고 Run 중 차단으로는 어차피 단절될 수 있다. |
| Isolated Node 허용 | 편집 중 상태와 단일 Node Map을 표현할 수 있다. | 이동에 참여하지 않는 Node와 Edge 누락 실수가 완성된 Map에 섞인다. |
| 빈 Map 허용 | 편집 시작점으로 사용할 수 있다. | 경로 탐색에 쓸 수 없고 완성된 immutable Map의 의미가 약해진다. |
| Cycle 거부 | 일부 graph 알고리즘이 단순해진다. | 양방향 통로와 순환 동선을 표현할 수 없어 실제 이동 Map에 맞지 않는다. |

## 다시 검토할 조건

- 제자리 행동을 routing graph에 포함해야 하는 실제 요구가 생긴 경우
- 같은 Node 사이의 여러 통로가 절대 존재하지 않는다는 제품 제약이 생긴 경우
- 모든 Map이 하나의 연결된 이동 구역이어야 한다는 제품 제약이 생긴 경우
- 이동하지 않는 위치도 routing Node로 표현해야 하는 실제 요구가 생긴 경우
- 빈 상태부터 수정하는 Map 편집 lifecycle을 domain이 직접 담당해야 하는 경우
- 이동 graph가 항상 단방향 비순환 구조여야 한다는 제품 제약이 생긴 경우
- 매우 큰 Map에서 생성 검증이 측정된 병목이 된 경우
