# 001. Map의 Edge를 방향성 있는 이동 관계로 모델링

- 상태: 채택
- 결정일: 2026-08-09

## 맥락

FleetLab의 Map은 path finding, dispatch, traffic control 실험의 입력이다. 일방통행과 방향별 거리·제약을 자연스럽게 표현할 Edge 모델이 필요하다.

## 결정

`Edge`를 `from` Node에서 `to` Node로 이동할 수 있음을 나타내는 directed edge로 정의한다. 양방향 통로는 반대 방향 Edge 두 개로 표현하며, 반대 방향 Edge의 존재나 속성 대칭을 강제하지 않는다.

| 통로 | Edge 표현 |
| --- | --- |
| A에서 B로 이동 | `A -> B` |
| 양방향 이동 | `A -> B`, `B -> A` |

## 선택의 장점

| 관점 | 장점 |
| --- | --- |
| 이동 규칙 | Edge의 존재만으로 일방통행을 표현한다. |
| 방향별 조건 | 거리, 속도 제한, 통행 상태를 방향마다 다르게 둘 수 있다. |
| PathPlanner | 현재 Node의 outgoing Edge만 순회하면 된다. |
| 실행 상태 | 한 방향만 차단하는 상태를 Edge 단위로 표현할 수 있다. |

## 감수하는 단점

| 단점 | 대응 |
| --- | --- |
| 양방향 통로는 Edge 두 개를 입력해야 한다. | 필요할 때 생성 API나 편집 기능에 양방향 입력 도우미를 둔다. |
| 반대 방향 Edge가 누락되거나 서로 다른 값을 가질 수 있다. | 방향별 조건이 실제로 다를 수 있으므로 대칭을 Map 불변조건으로 강제하지 않는다. |
| 두 Edge가 같은 물리적 통로를 공유한다는 의미는 없다. | traffic control에 필요해질 때 shared resource 또는 conflict zone을 별도로 모델링한다. |

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| Undirected Edge | 양방향 통로 입력이 간결하다. | 일방통행, 방향별 비용, 한 방향 차단에 별도 규칙이 필요하다. |
| 방향 속성을 가진 단일 Edge | 하나의 Edge로 세 방향 상태를 표현한다. | 방향별 속성과 runtime state가 늘면 조건 분기가 복잡해진다. |

## 아직 결정하지 않은 사항

- Map의 immutable 여부
- Edge 거리의 타입, 단위와 계산 방식
- Node와 Edge의 ID 타입
- parallel edge 허용 여부
- 물리적 통로와 충돌 영역 모델

## 다시 검토할 조건

- traffic control에서 반대 방향 Edge의 물리적 점유 관계가 필요해진 경우
- 지원할 Map이 항상 대칭적인 양방향 graph라는 제품 제약이 생긴 경우
