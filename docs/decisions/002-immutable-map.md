# 002. 생성된 Map을 immutable하게 유지

- 상태: 채택
- 결정일: 2026-08-10

## 맥락

하나의 Map을 여러 SimulationRun이 공유하더라도 각 Run의 장애와 통행 상태가 서로 영향을 주지 않아야 한다. 같은 Scenario와 seed로 실행한 결과도 재현할 수 있어야 한다.

## 결정

검증을 마쳐 생성된 Map과 그 안의 정적 Node·Edge 정보는 변경하지 않는다. Map을 편집할 때는 새로운 Map 또는 revision을 만들고, 외부의 mutable collection을 보관하거나 노출하지 않는다.

실행 중 변화는 Map이 아니라 SimulationRun별 runtime state에 둔다.

| 정적 Map | Run별 runtime state |
| --- | --- |
| Node와 Edge | Robot 위치 |
| 좌표와 거리 | 차단된 Edge |
| 이동 가능한 방향 | Edge 점유·예약, 장애와 혼잡 |

## 선택의 장점

| 관점 | 장점 |
| --- | --- |
| 재현성 | 실행 중 정적 실험 조건이 바뀌지 않는다. |
| Run 격리 | 한 Run의 상태가 다른 Run에 누출되지 않는다. |
| 동시 실행 | 여러 Run이 같은 Map을 안전하게 공유할 수 있다. |
| PathPlanner | 탐색 중 graph가 변경되는 상황을 고려하지 않아도 된다. |
| 테스트 | 고정된 입력으로 빠른 순수 unit test를 작성하기 쉽다. |

## 감수하는 단점

| 단점 | 대응 |
| --- | --- |
| Map을 직접 수정할 수 없다. | 편집 결과로 새 Map 또는 revision을 만든다. |
| 점진적인 생성이 불편할 수 있다. | 필요할 때 별도 draft나 편집 모델을 도입한다. |
| 큰 Map 수정 시 복사 비용이 생길 수 있다. | 실제 성능 문제가 확인되기 전에는 단순한 모델을 유지한다. |

## 검토한 대안

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| Mutable Map | Node와 Edge를 직접 추가·삭제하기 쉽다. | Run 간 상태 누출, 재현성 저하, 탐색 중 변경 위험이 생긴다. |
| Run마다 Map 복사 | Run 상태를 물리적으로 격리할 수 있다. | 정적 구조와 runtime 상태가 섞이고 불필요한 복사와 관리 비용이 생긴다. |

## 다시 검토할 조건

- 큰 Map의 revision 생성 비용이 실제 병목으로 확인된 경우
- Map 편집 요구가 구체화되어 별도 draft 모델이 필요한 경우
- 실행 중 topology 자체가 바뀌는 요구를 runtime state로 표현하기 어려운 경우
